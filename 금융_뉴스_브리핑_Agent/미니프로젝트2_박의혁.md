## 1. 시스템 개요

### 문제 정의
자산운용사 리서치팀의 일일 뉴스 수집 프로세스에서 발생하는 3가지 문제:
- **매체 편향**: 팀원마다 다른 뉴스 매체를 봐서 정보가 제각각
- **신호 대 잡음**: 대부분의 뉴스가 금융과 무관해 골라내는 데 시간 소모
- **중복 처리**: 어제 읽은 기사를 오늘 또 읽는 비효율

### 솔루션
**매일 아침 8시 30분, 4개 매체의 금융 뉴스만 요약해 Discord로 자동 발송**하고, 발송 이력을 Google Sheets에 누적 기록한다.

## 2. 전체 아키텍처

```
⏰ 매일 08:30 (Asia/Seoul, Schedule Trigger)
        │
        ▼
[RSS 수집] 연합뉴스 + 한국경제 + 매일경제 + 뉴시스 (병렬, Merge-Append)
        │
        ▼
[오늘_기사만] pubDate가 오늘인 기사만 필터
        │
        ▼
[중복_제거] Google Sheet 발송_이력과 URL 대조 (Merge, Keep Non-Matches)
        │
        ▼
[금융_필터] 포함/제외 키워드 정규식 필터
        │
        ▼
[AI Agent] Google Gemini + Structured Output Parser
        → summary / importance / category / needs_review / title / link (JSON)
        │
        ▼
[중요도_필터] importance ≥ 4
        │
   ┌────┴────┐
   ▼         ▼
[발송이력_기록]  [기사_모으기] → [메시지_조립] → [Discord_발송]
(Sheet Append)   (Aggregate)     (메시지 조립,     (Webhook)
                                  길이 제한 처리)

* 별도 워크플로우 "금융브리핑_에러알림": Error Trigger → Discord
  → 메인 워크플로우 Settings의 Error Workflow로 연결
  → 시스템 장애 시 별도 경고 메시지 발송 (REQ-06 대응)
```

## 3. RSS 피드 (REQ-01)

| 매체 | RSS 주소 |
|---|---|
| 연합뉴스 경제 | `https://www.yna.co.kr/rss/economy.xml` |
| 한국경제 | `https://www.hankyung.com/feed/economy` |
| 매일경제 | `https://www.mk.co.kr/rss/30100041/` |
| 뉴시스 경제 | `https://www.newsis.com/RSS/economy.xml` |

4개 매체를 병렬로 연결하고, **각 RSS 노드에 `On Error: Continue` 설정**을 적용했다. 한 피드가 응답하지 않거나 파싱에 실패해도 나머지 피드 데이터만으로 파이프라인이 계속 진행되어, 전체 브리핑이 멈추지 않는다.

## 4. 중복 발송 방지 (REQ-03)

### 고유값: URL

RSS의 `link` 필드(기사 원문 링크)를 고유값으로 채택했다.

**근거**:
- 같은 URL = 같은 기사라는 것이 100% 보장됨
- RSS 피드에서 매체 조작 없이 자동으로 추출됨
- 제목이 매체 편집으로 바뀌어도 URL은 변하지 않음 (Title 대비 강건함)
- 해시 등 별도 가공이 필요 없어 구현이 단순함

### 구현: LLM 호출 이전 차단

Google Sheets `발송_이력` 탭에서 과거 발송 기록 전체를 읽어온 뒤(`발송이력_조회`), **`중복_제거`(Merge 노드, Combine by Matching Fields: Input1의 `link` ↔ Input2의 `URL`, Output Type = Keep Non-Matches)** 로 이미 보낸 URL과 일치하는 기사를 제거한다. 이 단계는 `AI Agent`(LLM 호출) **이전**에 위치하여, 중복 기사가 LLM 비용을 발생시키지 않는다.

시트가 비어있는 첫 실행일에는 `발송이력_조회`에 `Always Output Data`를 켜두어, 데이터가 없어도 워크플로우가 중단되지 않고 모든 기사를 신규로 처리한다.

## 5. 금융 키워드 필터 (REQ-04)

### 필터 위치: LLM 호출 앞

**근거**:
- **비용 절감**: 금융과 무관한 기사는 LLM에 아예 전달되지 않아 API 호출 수가 크게 줄어듦
- **속도**: 정규식 매칭이 LLM 추론보다 훨씬 빠름
- **트레이드오프 인지**: 키워드에 없는 표현으로 쓰인 금융 기사는 사전 필터 단계에서 손실될 수 있음(위음성). 이는 필터 목록을 주기적으로 검토·보완하는 것으로 완화한다.

### 구현

`금융_필터` 노드(Filter, AND 결합 2개 조건)에서 기사의 `title + description(or contentSnippet)`을 대상으로:
1. **포함 키워드**(정규식 `matches regex`): 금리·통화정책, 증시, 환율, 부동산, 기업실적, 정책/규제, 경제지표 등 약 65개 단어
2. **제외 키워드**(정규식 `does not match regex`): 연예, 스포츠, 날씨, 영화, 게임 등 약 20개 단어

두 조건을 모두 만족해야 통과한다. (전체 정규식 패턴은 워크플로우 JSON 참고)

## 6. LLM 요약 및 중요도 분류 (REQ-05)

**모델**: Google Gemini (`models/gemini-3.5-flash`), n8n `AI Agent` 노드 + `Structured Output Parser`로 JSON 스키마 강제

**출력 스키마**:
```json
{
  "summary": "string, 3문장 이하",
  "importance": "integer, 1~5",
  "category": "증시 | 금리 | 환율 | 부동산 | 기업 | 정책 | 기타",
  "needs_review": "boolean",
  "title": "string (원문 제목 그대로 반환)",
  "link": "string (원문 링크 그대로 반환)"
}
```

`title`/`link`를 LLM 출력에 포함시킨 이유: LLM 노드가 원본 필드를 그대로 보존하지 않고 자체 출력으로 덮어쓰는 특성이 있어, 프롬프트에서 원본 값을 그대로 되돌려받도록 명시적으로 요청해 후속 단계(메시지 조립, 시트 기록)에서 제목·링크 유실을 방지했다.

**중요도 판정 기준**은 프롬프트에 5단계 전부 명시했다 (시장 전체를 흔드는 사건=5 ~ 브리핑 불필요=1).

## 7. Discord 브리핑 발송 (REQ-06)

### 메시지 통합
`중요도_필터`(importance ≥ 4)를 통과한 기사를 `기사_모으기`(Aggregate, 전체를 배열 하나로 병합)로 모은 뒤, `메시지_조립`(Set 노드, JS 표현식)에서 번호 매긴 목록 형태의 문자열 하나로 조립하여 Discord에 **메시지 1개**로 발송한다.

### 메시지 길이 제한 대응
Discord 메시지는 2,000자 제한이 있어, 기사 수가 많은 날 전부 담으면 발송이 실패한다. 이를 위해:
- 기사를 중요도 내림차순 정렬
- 누적 길이가 1,800자를 넘기 전까지만 본문에 포함
- 넘는 기사는 `"...외 N건은 발송 이력 시트에서 확인해주세요"`로 안내 (해당 기사들도 시트에는 전부 기록됨)

### 빈 브리핑 경로
중요 기사가 0건인 경우, 아래처럼 "정상 작동 중"임을 명시한 별도 메시지를 발송한다.

```
📊 오늘의 금융 브리핑 (YYYY-MM-DD)

오늘은 시장에 영향을 미칠 주요 소식이 없습니다.
(중요도 4 이상의 기사 0건)

시스템은 정상 작동 중입니다. ✅
```

### 시스템 장애와 "무소식"의 구분
위 "빈 브리핑" 메시지는 **워크플로우가 정상적으로 끝까지 실행된 결과**다. 반면 워크플로우 자체가 중간에 실패하는 경우(예: Google API 인증 만료, LLM API 장애)에는 이 메시지조차 발송되지 않으므로, 사용자가 "오늘은 조용한 날"과 "시스템 고장"을 구분할 수 없는 문제가 있었다.

이를 해결하기 위해 **별도의 에러 알림 워크플로우(`금융브리핑_에러알림`)**를 만들었다:
- `Error Trigger` 노드로 시작해, 메인 워크플로우의 어느 노드에서 실패하든 이를 감지
- 실패 시각·실패 노드·에러 메시지를 담아 같은 Discord 채널로 `⚠️ 금융 뉴스 브리핑 시스템에 오류가 발생했습니다` 메시지 발송
- 메인 워크플로우의 Settings → Error Workflow에 이 워크플로우를 연결

이 구조는 n8n의 Error Workflow가 **스케줄/웹훅 등 실제 트리거 실행에서만 동작하고 수동 실행(Execute workflow)에는 발동하지 않는다는 점**을 확인해, 스케줄 트리거를 임시로 앞당겨 발동시키는 방식으로 실제 검증했다.

## 8. 발송 이력 기록 (REQ-07)

`발송_이력` 시트에 아래 7개 컬럼을 매 발송 건당 자동으로 append한다.

| 컬럼 | 설명 |
|---|---|
| 발송시간 | ISO 8601 타임스탬프 |
| URL | 기사 원문 링크 (중복 제거의 기준값) |
| 제목 | 기사 제목 |
| 요약 | LLM이 생성한 요약 |
| 중요도 | 1~5 |
| 카테고리 | 증시/금리/환율/부동산/기업/정책/기타 |
| needs_review | LLM 자체 검증 플래그 |

이 기록은 다음 날 실행 시 `중복_제거` 단계의 대조 대상이 되므로, 절대 삭제하지 않는다.

## 11. 알게 된 점 / 설계 트레이드오프

- **키워드 필터의 위음성**: LLM 호출 전 필터링은 비용을 크게 줄이지만, 목록에 없는 표현의 금융 기사를 놓칠 수 있다. 100% recall보다 비용 효율을 우선한 설계 선택이다.
- **LLM 비결정성**: 같은 기사를 여러 번 넣으면 중요도 판정이 미세하게 달라질 수 있다. 다만 실제 운영에서는 기사당 LLM 호출이 1회로 고정되어(중복 제거가 먼저 동작하므로) 문제가 되지 않는다.
- **다중 입력 연결 주의**: n8n에서 한 노드에 의도치 않은 연결이 추가되면(예: 필터 결과가 후속 노드와 LLM 처리 노드 양쪽에 동시 연결) 해당 노드가 두 번 실행되어 데이터가 꼬일 수 있다. 워크플로우 JSON을 다운로드해 `connections` 항목을 점검하는 것이 캔버스 육안 확인보다 확실하다.
