# 10/16 작업 정리

## 한 줄 요약
에이전트 평가 도구를 만들고, 청킹·모델·검색·프롬프트를 바꿔 가며 평가해서
**정답률 0.81 → 0.90**으로 올렸다 (200문제 기준). 같은 조건의 기본 RAG(0.86)보다 4%p 높다.

## 오늘 한 것

### 1. 골든셋 합치기
- 제공 골든셋 267개 + 내 골든셋 77개 → `data/goldenset_all.csv` **309문제** (겹치는 35개는 한 번만)
- 빠르게 비교하려고 분야·근거 유형 비율을 맞춰 뽑은 `data/goldenset_200.csv` **200문제**도 만듦

### 2. 에이전트 평가 도구 만들기 (`pipeline/evaluate_agent.py`)
- 골든셋 문제를 에이전트에 하나씩 풀리고 채점
- 채점 항목: 답 정확도(LLM 채점, openevals), 근거 쪽 적중, 보류 판단, 검색 횟수, 응답 시간
- 중간에 끊겨도 다시 실행하면 이어서 풂

### 3. 코드 정리
- 여러 파일에 같은 코드가 반복되던 것을 공통 함수로 모음 (183줄 줄어듦)
- 정리 전후 추출·청크·검색 결과가 똑같은지 확인함
- BM25 색인을 파일로 저장해 두고 재사용 → 시작 시간 20초 → 0.2초

### 4. 모델 고르기
| 모델 | 질문당 시간 | 결과 |
|---|---|---|
| gemini-3.6-flash | 11초 | 잘함, 느림 |
| **gemini-3.5-flash-lite** | **4초** | **재검색·보류 잘함 → 선택** |
| gemini-2.5-flash / lite | 5초 | 재검색을 안 함, 보류 표시가 틀리기도 함 |

- 채점 모델도 3.5-flash-lite로 고정 (4개 모델 모두 채점은 정확했고 가장 빠름)

### 5. 청킹 비교 (300/50 · 500/60 · 800/100)
| 청킹 | 검색 점수 (MRR) | 에이전트 정답률 (2회) |
|---|---|---|
| 300/50 | **0.830** | 0.786 / 0.796 |
| **500/60** | 0.819 | **0.827 / 0.811** |
| 800/100 | 0.812 | 0.806 |

- 검색 점수는 300/50이 좋았지만, 실제 답 정확도는 500/60이 두 번 다 높아서 **500/60 선택**
- 배운 점: 검색 점수만 보고 청킹을 고르면 안 된다

### 6. 왜 틀리는지 분석 (RAGAS + agentevals)
- **RAGAS**: 틀린 34문제 중 24개는 **검색 문제**
  - 맞는 쪽은 찾았는데, 그 쪽에서 답이 적힌 조각은 못 가져옴
  - 그래서 "근거가 없다"며 보류 → 에이전트 판단은 오히려 맞았음
  - 답을 지어내는 문제는 거의 없었음
- **agentevals** (검색 과정 채점)
  - 분야(domain)를 잘못 고르면 정답률 0.3 수준
  - 표 질문에 쓰던 MMR 검색이 오히려 불리했음 (표의 한 줄만 가져옴)

### 7. 검색 고치기
| 바꾼 것 | 정답률 |
|---|---|
| 처음 | 0.827 / 0.811 |
| ① 찾은 조각의 앞뒤 조각도 같이 넘기기 | 0.806 |
| ① + ② 표 질문도 일반 검색(Hybrid) | 0.842 |
| **① + ② + ③ 분야를 골라도 전체 결과 섞기** | **0.872 / 0.898** |

### 8. 프롬프트 고치기 (p1 → p2)
- 표 숫자로 계산할 수 있으면 계산해서 답하기 ("비교 문장이 없다"며 보류하지 않기)
- 질문이 여러 부분이면 빠짐없이 답하기
- 질문과 연도·대상·단위가 같은 숫자 쓰기
- 결과: 정답률 **0.888 / 0.903**, 표 질문 0.67~0.76 → **0.818**
- 답이 없는 문제는 여전히 100% 보류 (억지로 답하지 않음)

### 9. 기본 RAG와 비교 (과제 필수)
- 기본 RAG: 질문 그대로 **한 번만** 검색하고 바로 답변/보류
- 검색 방법·모델·답변 규칙은 에이전트와 똑같이 하고, **다시 찾기·검색어 고르기만 뺌**

| | 에이전트 1차 / 2차 | 기본 RAG 1차 / 2차 |
|---|---|---|
| 200문제 중 맞음 | **178 / 181** | 174 / 169 |
| 정답률 (답 있는 196문제) | **0.888 / 0.903** | 0.867 / 0.842 |
| 답했는데 틀림 | 9 / 7 | 8 / 12 |
| 답이 있는데 보류 | **13 / 12** | 18 / 19 |
| 답 없는 문제 보류 | 100% | 100% |
| 표 질문 정답률 | **0.818 / 0.818** | 0.758 / 0.697 |
| 평균 검색 / 시간 | 1.3회 / 4.1초 | 1회 / **2.4초** |

- 에이전트가 평균 **약 4%p 더 맞힘** (0.896 vs 0.855), 대신 **약 1.7배 느림**
- 차이는 주로 보류에서 남: 기본 RAG는 한 번 못 찾으면 바로 보류, 에이전트는 다시 찾아서 줄임
- 두 번 다 에이전트만 맞힌 문제 9개 / 기본 RAG만 맞힌 문제 3개
  - 9개 중 5개는 **다시 찾기**(2~3번 검색) 덕분
  - 4개는 한 번만 검색했지만 질문 대신 **핵심어로 검색어를 다듬어서** 찾음 → 검색어 고르기도 효과
- 에이전트도 76%의 문제는 한 번 검색으로 끝냄 → 다시 찾기는 어려운 문제에서만 쓰임

### 10. 언제 기본 RAG, 언제 에이전트?

**섞어 쓰기 추정** (저장된 두 결과를 조합해서 계산한 값, 실제로 돌린 것은 아님)

| 방식 | 정답률 1차 / 2차 | 평균 시간 |
|---|---|---|
| 기본 RAG만 | 0.867 / 0.842 | **2.4초** |
| 에이전트만 | 0.888 / **0.903** | 4.1초 |
| **섞기** (기본 RAG가 보류하면 에이전트로 넘김) | **0.908** / 0.893 | **3.0초** |

- 200문제 중 22~23개만 에이전트로 넘어감 → 에이전트만큼 정확하고 시간은 약 25% 줄어듦

| 기본 RAG가 좋을 때 | 에이전트가 좋을 때 |
|---|---|
| 질문이 짧고 단순함 (정의·사실 하나) | 질문이 여러 부분 (목적과 활동, 금액과 변화율) |
| 질문 표현이 문서와 비슷함 | 질문 표현이 문서와 다름 ("속이 쓰려요" → "위산 속쓰림") |
| 빠른 응답이 중요 (채팅 상담) | 표·숫자 계산이 필요 |
| 사용자가 많아 비용이 중요 | 틀린 답이 큰 문제 (의료·법률·금융) |
| 틀려도 큰 문제가 없음 | 한 번에 못 찾는 경우가 많음 |

- 쉬운 질문과 어려운 질문이 섞여 있으면 → **섞기** (쉬운 건 빠르게, 어려운 것만 에이전트)
- 이 프로젝트는 의료·법률·금융 문서 + 표 질문이 많아 **에이전트**, 속도까지 챙기려면 섞기

## 한계점

**평가 방법의 한계**
- **결과가 매번 조금씩 흔들린다**: 같은 설정을 두 번 돌려도 정답률이 1~2%p 다름. 그래서 프롬프트 개선(+1%p)처럼 작은 차이는 확실하다고 말하기 어려움
- **비교는 200문제로, 설정마다 1~2번만 돌림**: 더 많이 돌리면 더 믿을 만함
- **채점도 LLM이 함**: 가끔 잘못 판정할 수 있음. 채점 모델은 12문제로만 확인함 (그때 3.6-flash가 불완전한 답을 정답으로 봐준 적도 있음)
- **응답 시간은 동시에 몇 개를 돌렸는지에 따라 달라짐**: 시간 비교는 대략적으로만 봐야 함

**골든셋의 한계**
- **답이 없는 문제가 4개뿐**: "지어내지 않는다"를 보여주기엔 부족. 특히 p2의 "계산해서 답하라" 규칙이 억지 답변을 늘리는지는 이 4문제로 충분히 시험하지 못함
- **정답이 이상해 보이는 문제가 있음**: 예) "가장 비율이 높은 주주"의 정답이 "기타 주주". 정답이 틀리면 맞게 답해도 오답 처리됨
- **정답 쪽이 하나만 적힌 문제가 많음**: 같은 내용이 다른 쪽에도 있으면 맞는 근거를 대도 "근거 쪽 적중"에서 빠짐 (예: DC 퇴직연금 질문, 정답 p.27인데 p.32를 근거로 듦)

**실험 설계의 한계**
- **청킹 비교는 처음 검색 방식에서 했음**: 검색을 바꾼 뒤에 300/50·800/100을 다시 비교하지는 않음
- **검색 개선은 하나씩 더해 가며 시험함**: ②표 Hybrid, ③분야 보완을 따로따로 시험하지는 않아서 각각의 순수 효과는 모름
- **3.6-flash는 전체 평가를 안 함**: 모델 선택은 3문제 속도 비교와 12문제 결과로 정함. 정답률은 3.6-flash가 더 높을 수도 있음
- **RAGAS 분석은 표본으로 함**: 실패 34개 + 성공 34개, 채점도 lite 모델

**아직 해결 못 한 것**
- **그래프·이미지 속 숫자**: 남은 "답이 있는데 보류" 대부분이 여기. 추출 단계 문제라 검색·프롬프트로는 못 고침
- **기본 RAG 비교는 최종 설정에서만 함**: 처음 설정(300/50, 처음 검색)에서도 에이전트가 이득이었는지는 모름
- **에이전트 이득 4%p 중 다시 찾기와 검색어 고르기의 몫을 따로 재지는 않음**

**분석하면서 바로잡은 것**
- 처음에는 "실패의 약 70%가 판단 문제"라고 봤지만, RAGAS로 보니 대부분 **검색 문제**였음
  (정답 "쪽"을 찾은 것과 답이 적힌 "조각"을 찾은 것은 다름 → 쪽 단위 지표만 보면 원인을 잘못 짚을 수 있음)

## 알게 된 것
- RAG는 추출 → 검색 → 답변 단계마다 조금씩 놓쳐서 100%는 거의 안 나온다
- 같은 설정도 돌릴 때마다 1~2%p 흔들린다 → 중요한 비교는 두 번 돌려서 확인
- 틀린 답보다 보류가 많다 = 모르면 지어내지 않는다 (좋은 방향)
- 에이전트는 기본 RAG보다 정확하지만 느리다 → 정확도가 중요하면 에이전트, 속도가 중요하면 기본 RAG
