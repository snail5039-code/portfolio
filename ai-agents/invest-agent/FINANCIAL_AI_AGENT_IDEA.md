# 금융 AI 투자·검증 에이전트 프로젝트

## 한 줄 정의

재무제표·공시·뉴스·시장 데이터를 스스로 조사해 금융 판단을 만드는 **투자 에이전트**, 그 판단의 수치·근거·논리를 독립적으로 검사하는 **검증 에이전트**, 검증된 결정을 금융 업무로 옮기는 **실행 에이전트**가 협업하는 서비스다. 사용자가 미리 정한 권한 안에서는 자동 실행하고, 그 범위를 벗어나면 승인받는다.

## 해결하려는 문제

기존 투자 AI는 분석 결과를 생성해도 다음 문제를 사용자가 확인하기 어렵다.

- 재무 수치와 계산이 실제 공시와 일치하는지
- 오래된 자료나 근거 없는 뉴스를 사용했는지
- 분석과 실제 투자 행동이 논리적으로 연결되는지
- AI가 자신의 초기 판단을 정당화하려고 불리한 정보를 무시했는지
- 서로 충돌하는 정보가 있을 때 누가 최종 결정을 내려야 하는지

이 프로젝트는 투자 판단을 생성하는 AI와 이를 검증하는 AI를 분리해 한 에이전트에 분석·검증·실행 권한이 모두 집중되지 않도록 한다.

## 핵심 에이전트

### 1. 투자 에이전트

사용자가 설정한 투자 목표와 위험 한도 안에서 필요한 자료를 스스로 수집하고 투자안을 만든다.

- DART 공시 및 재무제표 수집
- 매출, 영업이익, 현금흐름, 부채, 밸류에이션 계산
- 최근 뉴스와 산업·거시경제 환경 분석
- 투자 후보 탐색 및 종목별 근거 작성
- 목표 비중, 진입 조건, 손절·재검토 조건 제안
- 검증을 통과한 경우 모의투자 또는 승인 요청 생성

투자 에이전트는 단순히 `매수`라고 출력하지 않고 다음과 같은 구조화된 투자 제안서를 제출한다.

```text
행동: 매수 / 매도 / 보유 / 관찰
대상 및 목표 비중:
판단 시점과 데이터 기준일:
핵심 근거:
사용한 원문 출처:
계산 과정:
반대 근거와 주요 위험:
판단이 무효가 되는 조건:
```

### 2. 검증 에이전트

투자 에이전트와 독립된 문맥에서 투자안을 감사한다. 처음부터 같은 결론을 공유하지 않고 원문 데이터를 다시 확인한다.

- 재무 수치, 단위, 계산식 재검산
- 전년 대비와 전분기 대비 등 기준 혼동 검사
- 출처가 실제 주장을 뒷받침하는지 확인
- 최신 공시 누락 및 오래된 데이터 사용 탐지
- 사실, 추론, 예측을 문장 단위로 분리
- 과도한 확신, 확증편향, 위험 누락 검사
- 투자 행동이 사용자 위험 한도와 맞는지 확인
- 반대 시나리오와 대안 행동 제시

검증 결과는 `승인`, `조건부 승인`, `반려`, `사용자 판단 필요` 중 하나로 반환한다.

### 3. 실행 에이전트

투자안과 검증 결과가 모두 준비된 뒤에만 작동한다. 스스로 투자 판단을 바꾸지 않고 승인된 행동을 금융기관 API가 요구하는 정확한 명령으로 변환한다.

- 모의 또는 실제 매수·매도 주문
- 정기 투자와 포트폴리오 리밸런싱
- 예금·대출·카드 납부 일정 관리
- 사용자가 허용한 계좌 사이의 이체
- 환율 조건에 따른 환전 예약
- 실행 전 잔액, 한도, 시장 상태 및 중복 요청 확인
- 실행 결과와 실패 사유 기록

실행 에이전트는 `자동 실행`, `간편 승인`, `강화 승인`, `실행 금지` 중 하나의 실행 등급을 적용한다. 실행 직전에는 투자 판단이 아니라 권한과 안전 조건만 다시 확인한다.

## 에이전트 간 상호 검증 흐름

```text
사용자 목표·위험 한도·실행 권한 설정
          ↓
투자 에이전트가 자료 조사 및 투자안 작성
          ↓
검증 에이전트가 독립적으로 수치·출처·논리 감사
          ↓
   ┌──────┴────────┐
 검증 통과          문제 발견
   ↓                  ↓
실행 정책 확인       투자 에이전트에 반박과 수정 요구
   ↓                  ↓
실행 에이전트         수정안 재검증
   ↓                  ↓
자동 실행/승인 요청  합의 실패·불확실성·정책 충돌
   ↓                  ↓
결과·감사 로그 저장   사용자에게 질문
```

검증 에이전트는 투자 에이전트에게 다음과 같이 질문할 수 있다.

- 왜 이 지표를 다른 지표보다 중요하게 평가했는가?
- 해당 수치의 기준일과 원문 위치는 어디인가?
- 악재가 발생했는데도 목표 비중을 유지한 이유는 무엇인가?
- 더 낮은 위험의 대안보다 이 행동이 적합한 이유는 무엇인가?
- 이 판단이 틀렸다고 인정할 객관적인 조건은 무엇인가?

## 사용자에게 질문하는 조건

모든 사소한 차이를 사용자에게 넘기지 않는다. 다음과 같이 사용자의 가치판단이나 새로운 권한이 필요한 경우에만 질문한다.

1. 두 에이전트가 정해진 재검증 횟수 이후에도 합의하지 못한 경우
2. 신뢰할 수 있는 최신 데이터가 부족하거나 원문끼리 충돌하는 경우
3. 예상 손실이나 포트폴리오 비중이 사용자 위험 한도를 넘는 경우
4. 기존 투자 목표와 새로운 행동이 충돌하는 경우
5. 매수·매도·보유의 기대 결과 차이가 오차 범위 안에 있는 경우
6. 실제 주문처럼 되돌리기 어렵거나 금전적 영향이 큰 행동인 경우

질문에는 선택지뿐 아니라 각 선택의 예상 결과와 두 에이전트의 의견 차이를 함께 표시한다.

## 자동 실행과 승인 기준

사용자가 처음에 `행동 종류`, `1회 한도`, `일일 한도`, `대상 자산`, `허용 시간`, `최대 손실`을 직접 설정한다. 에이전트가 이 권한을 임의로 확대할 수는 없다.

| 실행 등급 | 예시 | 처리 방식 |
|---|---|---|
| 자동 실행 | 소액 정기 투자, 허용 비율 내 리밸런싱, 모의주문 | 검증 통과 후 즉시 실행하고 알림 |
| 간편 승인 | 평소 범위의 신규 종목 매수, 조건부 환전 | 핵심 근거와 금액을 보여주고 1회 승인 |
| 강화 승인 | 고액 주문, 급격한 비중 변경, 외부 계좌 이체 | 추가 인증과 명시적 최종 확인 |
| 실행 금지 | 검증 실패, 한도 초과, 데이터 불확실, 시스템 이상 | 실행하지 않고 사용자에게 사유 보고 |

승인 화면에는 행동, 금액, 예상 비용, 핵심 근거, 반대 근거, 최악 시나리오, 검증 상태, 취소 가능 여부를 표시한다. 일정 시간 동안 승인하지 않으면 요청은 자동 만료하며, 침묵을 승인으로 간주하지 않는다.

## 금융 업무 실행 상태

금융 API의 요청 성공만으로 업무가 완료됐다고 판단하지 않는다.

```text
제안됨 → 검증됨 → 승인 대기 → 주문 제출 → 접수됨
                                  ↓
                         체결/완료 또는 실패/취소
```

- 모든 요청에 고유 실행 ID를 부여해 중복 주문과 중복 이체를 방지한다.
- 가격이나 환율이 승인 시점보다 크게 변하면 기존 승인을 폐기하고 다시 묻는다.
- 부분 체결, API 지연, 시장 휴장, 잔액 부족을 별도 상태로 처리한다.
- 실행 뒤 영수증·주문번호·체결가격을 저장하고 사용자에게 알린다.
- 검증 에이전트는 계획한 행동과 실제 결과가 일치하는지 사후 감사한다.

## 통합 투자 대시보드

사용자는 여러 에이전트의 내부 대화를 전부 읽지 않아도 현재 자산 상태, 성과 원인, 위험, 실행 내역을 한 화면에서 파악할 수 있어야 한다.

### 1. 자산 현황

- 총 보유자산과 현재 투자금액
- 현금, 주식, ETF 및 채권별 금액
- 종목·산업·국가·통화별 투자 비중
- 매수 원금, 현재 평가금액, 실현손익, 미실현손익
- 오늘·이번 달·올해·전체 기간 수익률
- 입출금 영향을 제외한 순수 투자수익률

### 2. 성과와 손익 분석

- 어떤 종목이 전체 수익과 손실에 얼마나 기여했는지
- 배당, 이자, 매매차익, 환차익을 구분한 수익
- 수수료, 세금, 환전비용을 반영한 실제 순손익
- 시장 상승으로 얻은 수익과 AI 판단으로 얻은 초과수익 구분
- 벤치마크 대비 성과, 변동성, 최대 낙폭
- 투자 에이전트 단독 판단과 검증 후 판단의 성과 비교

### 3. 기업 재무지표 분석

보유 종목과 투자 후보별로 다음 지표의 현재 값, 과거 추이, 산업 평균을 함께 보여준다.

- 매출액, 영업이익, 순이익, 영업이익률
- 영업현금흐름과 잉여현금흐름
- 부채비율, 유동비율, 이자보상배율
- ROE, ROA, EPS
- PER, PBR, PSR, EV/EBITDA
- 배당수익률과 배당성향

숫자만 나열하지 않고 `개선`, `악화`, `주의`, `산업 평균 대비 높음/낮음`을 표시하며, 각 지표를 누르면 공시 원문과 계산식을 확인할 수 있게 한다.

### 4. AI 판단과 검증 상태

- 투자 에이전트의 최신 행동 제안과 핵심 근거
- 검증 에이전트가 발견한 오류·반대 근거·누락 위험
- 현재 합의 상태와 신뢰도
- 자동 실행, 승인 대기, 반려된 금융 업무
- 매수 당시의 판단과 현재 결과 비교
- 판단이 무효가 되는 조건의 충족 여부

### 5. 위험 관제

- 종목·산업 쏠림과 상관관계
- 예상 최대 손실과 최대 낙폭
- 실적 발표, 배당락, 만기, 금리 결정 등 주요 일정
- 손절·리밸런싱·현금 부족 조건 접근 알림
- 데이터 지연, 검증 실패, 금융 API 장애 경고

### 화면 구성 예시

기준 디자인은 **macOS 네이티브 금융 애플리케이션**으로 확정한다. 일반적인 웹 대시보드처럼 둥근 카드와 KPI 박스를 반복하지 않고, macOS의 통합 타이틀바·소스 리스트·분할 화면·인스펙터 구조를 사용한다.

```text
┌──────────────┬───────────────────────────────────────┐
│ macOS        │  투자 운영                  검색 ···│
│ 사이드바     ├──────────────────────────┬────────────┤
│              │ 총자산과 손익 추이        │ 에이전트   │
│ 포트폴리오   │                          │ 실행 기록  │
│ 계좌         │ 보유 종목 목록            │            │
│ 거래 내역    │                          │ 분석       │
│              │                          │   ↓        │
│ 분석 에이전트│                          │ 검증       │
│ 검증 에이전트│                          │   ↓        │
│ 실행 에이전트│                          │ 실행/승인  │
│ 투자 리포트  │                          │            │
└──────────────┴──────────────────────────┴────────────┘
```

#### 디자인 원칙

- Apple Stocks의 `사이드바 → 차트 → 종목 정보` 구조와 macOS 생산성 앱의 인스펙터 패턴을 결합한다.
- 시스템 글꼴, 얇은 구분선, 작은 행 간격, 통합 타이틀바를 사용해 실제 데스크톱 앱처럼 보이게 한다.
- 그라데이션, 네온 색상, 과도한 그림자, 큰 둥근 카드, 의미 없는 상태 배지를 사용하지 않는다.
- 색상은 상승·하락·경고·선택 상태처럼 의미가 있을 때만 제한적으로 사용한다.
- 정보는 카드 여러 개로 분산하지 않고 차트, 표, 문서, 인스펙터의 연속적인 작업 화면으로 제공한다.
- AI를 숨기지는 않는다. `분석 에이전트 → 검증 에이전트 → 실행 에이전트`의 흐름과 반론·근거·승인 상태를 우측 인스펙터에 명확히 표시한다.
- 에이전트 대화는 메신저 채팅처럼 표현하지 않고 금융 업무 기록, 근거 문서, 검증 결과, 주문 상태로 표현한다.
- 라이트 모드와 다크 모드를 모두 지원하며 창이 좁아지면 우측 인스펙터부터 접는다.

#### 투자 운영 화면

- 좌측 사이드바: 포트폴리오, 계좌, 거래 내역, 세 에이전트, 투자 리포트
- 중앙 상단: 총자산, 당일 손익, 기간별 자산 변화 차트
- 중앙 하단: 보유 종목, 수량, 평가금액, 실현·미실현손익
- 우측 인스펙터: 분석 에이전트의 제안, 검증 에이전트의 반론과 재계산, 실행 에이전트의 주문 조건
- 자동 실행 기준을 충족하지 못한 주문은 인스펙터 하단에서 사용자가 승인하거나 반려한다.

현재 합의한 인터랙티브 목업의 투자 운영 화면을 기준으로 실제 프론트엔드를 구현한다. 토큰증권 화면과 설계는 별도 문서 `TOKEN_SECURITIES_AI_PROJECT.md`에서 관리한다.

대시보드의 모든 금액과 지표에는 `기준 시각`, `원본 데이터 출처`, `마지막 검증 시각`을 표시한다. 실시간 시세와 최신 공시의 갱신 주기가 다르므로 하나의 시점 데이터처럼 오해하지 않게 한다.

## 투자 리포트

대시보드가 현재 상태를 빠르게 확인하는 화면이라면, 투자 리포트는 일정 기간 동안의 판단·실행·성과를 근거와 함께 정리하는 최종 산출물이다. 주간·월간·분기별로 자동 생성하고, 중요한 시장 변화나 위험 한도 초과가 발생하면 수시 리포트를 만든다.

### 리포트 구성

1. **요약**
   - 총자산, 투자원금, 평가금액
   - 실현·미실현손익과 순수익률
   - 벤치마크 대비 성과
   - 현재 위험 수준과 가장 중요한 변화
2. **포트폴리오 현황**
   - 자산·종목·산업·국가·통화별 비중
   - 신규 편입, 비중 확대·축소, 청산 내역
   - 현금 비중과 투자 가능 금액
3. **성과 원인 분석**
   - 수익·손실 기여도가 큰 종목
   - 시장 요인과 AI 판단에 의한 성과 구분
   - 배당·이자·환율·수수료·세금의 영향
4. **재무지표와 투자 근거 변화**
   - 보유 기업의 핵심 재무지표 추이
   - 최초 투자 근거가 유지되는지 여부
   - 새로 발견된 호재·악재와 공시 원문
5. **에이전트 의사결정 감사**
   - 투자 에이전트가 제안한 행동
   - 검증 에이전트의 반박과 수정 요구
   - 최종 승인·실행 결과
   - 사용자가 개입한 결정과 그 이유
6. **위험과 다음 행동**
   - 최대 낙폭, 변동성, 집중도 및 주요 일정
   - 투자 판단을 무효화할 수 있는 조건
   - 유지·관찰·리밸런싱·매도 후보
   - 다음 기간에 사용자 승인이 필요한 사항

모든 리포트 문장에는 `검증된 사실`, `AI의 해석`, `미래 시나리오` 중 하나의 유형을 표시한다. 수치와 주장은 클릭하면 데이터 기준일, 계산식, 공시·뉴스 원문, 검증 결과까지 추적할 수 있게 한다.

### 리포트 생성·승인 흐름

```text
투자·실행·성과 기록 집계
          ↓
투자 에이전트가 초안 작성
          ↓
검증 에이전트가 수치·출처·성과 귀인 감사
          ↓
오류 수정 및 재검증
          ↓
최종 투자 리포트 발행
          ↓
사용자 피드백과 승인 결과를 다음 투자 정책에 반영
```

리포트는 화면 열람과 PDF 내보내기를 지원하는 것을 목표로 하되, 초기 MVP에서는 웹 리포트를 먼저 구현한다.

## 전체 서비스 운영 사이클

이 프로젝트는 한 번 분석하고 끝나는 도구가 아니라 다음 과정이 계속 순환하는 금융 업무 시스템이다.

```text
① 사용자 목표·위험 한도·자동 실행 권한 설정
                    ↓
② 금융 데이터 수집 및 상태 감시
                    ↓
③ 투자 에이전트의 분석과 투자안 작성
                    ↓
④ 검증 에이전트의 독립 감사·반박·재검증
                    ↓
⑤ 자동 실행 또는 사용자 승인
                    ↓
⑥ 실행 에이전트의 금융 업무 처리
                    ↓
⑦ 체결·잔고·손익·위험 실시간 추적
                    ↓
⑧ 검증된 주간·월간·분기 투자 리포트
                    ↓
⑨ 사용자 피드백 및 투자 정책 수정
                    └──────────────→ ②로 반복
```

최종 서비스의 핵심 가치는 단순한 자동매매가 아니라 **분석 근거부터 실제 실행, 성과, 사후 책임까지 전 과정을 추적하고 검증할 수 있다는 것**이다.

## 실제 구현 가능성 및 외부 API

### 결론

- **국내 상장주식 모의투자 MVP:** 현재 공개된 공식 API로 구현 가능
- **개인 계좌 실거래:** 증권사 계좌와 API 키가 있으면 기술적으로 가능하지만, 서비스로 타인의 자산을 자문·일임 운용하려면 별도의 규제·인가 검토가 필요
- **은행 계좌 조회·이체:** 오픈뱅킹 API가 존재하지만 정식 이용기관 계약, 사용자 인증·동의 및 보안 심사가 필요

### 데이터 및 실행 API

| 목적 | 후보 API | 사용 가능한 기능 | MVP 판단 |
|---|---|---|---|
| 공시·재무제표 | [금융감독원 OpenDART](https://opendart.fss.or.kr/intro/main.do) | 공시 검색, 원문 XML, 주요 재무계정, 정기보고서, 지분·주요사항 정보 | 필수, 바로 사용 가능 |
| 주가·주문·잔고 | [한국투자증권 Open API](https://apiportal.koreainvestment.com/) | 국내·해외주식, ETF/ETN, 채권의 시세·주문·잔고·체결과 모의투자 | 실행 에이전트 1순위 |
| 대체 증권사 | [키움 REST API](https://openapi.kiwoom.com/guide/apiguide) | 국내·미국주식 시세, 계좌, 주문, 실시간 데이터 및 모의투자 도메인 | 대체 또는 교차 검증용 |
| 시장 통계 | [KRX Data Marketplace](https://openapi.krx.co.kr/contents/OPP/MAIN/main/index.cmd) | 주식·지수·ETF·채권·파생·ESG 통계 | 벤치마크와 시장 비교용 |
| 거시경제 | [한국은행 ECOS](https://ecos.bok.or.kr/api/) | 금리, 환율, 물가, 통화 및 경제통계 | 거시 분석 에이전트용 |
| 계좌·송금 | [금융결제원 오픈뱅킹](https://openapi.kftc.or.kr/service/openBanking) | 잔액·거래내역, 입금·출금이체, 카드·대출 등 | 데모는 테스트 API, 상용화는 기관 계약 필요 |

OpenDART는 재무제표 숫자뿐 아니라 원문 XML도 제공하므로, 투자 에이전트가 구조화된 재무계정을 계산하고 검증 에이전트가 원문 문맥을 다시 확인하는 데 사용할 수 있다. 한국투자증권 Open API는 REST와 WebSocket, 모의·실전 앱키를 제공하며 공식 저장소에 잔고·주문·시세 및 LLM 연동 예제가 있다.

### API별 주의사항

- 공시 정정이 발생할 수 있으므로 접수번호, 보고서 버전, 기준일을 저장한다.
- 연결·별도재무제표와 누적·당기 값을 혼동하지 않도록 계정 표준화 계층을 둔다.
- 실시간 시세의 재배포와 상업적 이용은 거래소·증권사의 데이터 이용조건을 별도로 확인한다.
- 주문 API 성공 응답과 실제 체결은 다르므로 체결내역을 다시 조회한다.
- 증권사 호출 한도에 맞춰 캐시, 호출 큐, WebSocket 구독을 사용한다.
- 오픈뱅킹은 공개 문서가 있다고 개인 개발자가 곧바로 실제 이체를 수행할 수 있는 구조가 아니다. MVP에서는 테스트 환경이나 가상 계좌를 사용한다.

### 에이전트별 API 연결

| 에이전트 | 호출 대상 | 대표 작업 |
|---|---|---|
| 투자 에이전트 | OpenDART | 공시 검색, 기업 개황, 재무제표, 원문 XML 조회 |
| 투자 에이전트 | KRX·증권사 시세 API | 현재가, 일봉, 거래량, 지수, ETF·채권 정보 조회 |
| 투자 에이전트 | 한국은행 ECOS | 기준금리, 환율, 물가 및 거시경제 지표 조회 |
| 검증 에이전트 | OpenDART·별도 계산 API | 원문 재조회, 재무계정·단위·기준기간·계산식 검증 |
| 정책 엔진 | 내부 권한·위험 API | 종목·금액·손실·일일 거래·자동 실행 한도 확인 |
| 실행 에이전트 | 증권사 주문 API | 주문 가능 금액, 매수·매도, 정정·취소, 체결 조회 |
| 실행 에이전트 | 증권사 계좌 API | 잔고, 보유 수량, 평균단가, 평가손익, 주문내역 조회 |
| 금융업무 확장 | 금융결제원 오픈뱅킹 | 사용자 인증, 계좌 등록, 잔액·거래내역, 입출금이체 |
| 리포트 에이전트 | 내부 포트폴리오 API | 손익·성과·재무지표·판단·검증·체결 기록 집계 |

### 자동투자 API 처리 순서

```text
1. OpenDART·시세·ECOS 데이터 조회
2. 내부 계산 API로 재무지표와 위험지표 계산
3. 투자 에이전트가 구조화된 투자 제안 생성
4. 검증 에이전트가 원문과 계산 결과를 독립적으로 재검증
5. 정책 API가 사용자 권한·금액·손실 한도 확인
6. 자동 실행 또는 사용자 승인 토큰 발급
7. 실행 에이전트가 주문 가능 여부·잔고 재조회
8. 증권사 주문 API 호출
9. 주문번호로 접수·체결·부분체결·취소 상태 조회
10. 잔고와 손익을 동기화하고 리포트 생성
```

주문 API에는 LLM의 자연어를 직접 전달하지 않는다. 투자·검증 결과를 다음과 같은 제한된 내부 명령으로 변환한 뒤 정책 엔진을 통과시킨다.

```json
{
  "action": "BUY",
  "symbol": "005930",
  "quantity": 10,
  "order_type": "LIMIT",
  "limit_price": 70000,
  "max_slippage_pct": 0.3,
  "expires_at": "2026-08-25T15:00:00+09:00",
  "decision_id": "dec_001",
  "verification_id": "ver_001",
  "approval_mode": "AUTO_WITHIN_LIMIT"
}
```

실행 서비스는 허용된 명령과 필드만 받아들이며 `decision_id`, `verification_id`, 사용자 승인 또는 자동 실행 권한이 모두 유효한 경우에만 증권사 API를 호출한다.

### 모의투자와 실거래 환경 분리

```text
공통 분석·검증 시스템
        ↓
거래 어댑터 인터페이스
   ┌────┴────┐
모의투자 API  실거래 API
```

- 개발·테스트 기본값은 항상 모의투자로 둔다.
- 모의와 실전의 앱 키, 계좌번호, 서버 주소, 데이터베이스를 분리한다.
- 실거래 전환은 환경변수 하나로 바꾸지 못하게 하고 별도 배포·인증 절차를 둔다.
- 실행 에이전트가 어느 환경인지 주문 전후 화면과 로그에 명확하게 표시한다.
- 모의투자에서 검증하지 않은 전략은 실거래 실행 권한을 받을 수 없게 한다.

### 내부 서비스 API 초안

외부 금융 API를 에이전트가 직접 제각각 호출하지 않고 내부 게이트웨이로 감싼다.

| 내부 엔드포인트 | 역할 |
|---|---|
| `GET /companies/{code}/filings` | 기업 공시와 원문 메타데이터 조회 |
| `GET /companies/{code}/financials` | 표준화된 재무계정과 계산 근거 조회 |
| `GET /market/{code}/quote` | 현재가와 데이터 기준 시각 조회 |
| `POST /analysis/proposals` | 투자 제안 생성 및 저장 |
| `POST /verifications` | 독립 검증 실행 |
| `POST /policies/check` | 위험 한도와 자동 실행 권한 검사 |
| `POST /approvals` | 사용자 승인 생성·확인·만료 처리 |
| `POST /orders` | 검증된 주문 제출 |
| `GET /orders/{id}` | 접수·체결·실패·취소 상태 조회 |
| `GET /portfolios/{id}` | 보유자산, 원금, 평가금액, 손익 조회 |
| `POST /reports` | 검증된 투자 리포트 생성 |

## AI 개발 및 학습 전략

### 에이전트 오케스트레이션: LangGraph 중심

이 프로젝트에는 **LangGraph를 핵심 오케스트레이터로 사용**하고, LangChain은 모델·도구·RAG 연결이 편리한 부분에 선택적으로 사용한다.

- **LangChain:** LLM, 임베딩, 벡터 검색, 문서 로더, 도구 호출을 공통 인터페이스로 연결하는 상위 프레임워크
- **LangGraph:** 여러 에이전트와 금융 업무의 실행 순서, 반복, 분기, 중단, 재개 및 상태 저장을 그래프로 관리하는 런타임
- **LangSmith 또는 자체 추적 시스템:** 에이전트 호출, 도구 사용, 오류, 지연시간 및 평가 결과 추적. 금융 판단 원문과 개인정보는 외부 전송 정책을 먼저 검토한다.

LangChain의 에이전트도 내부적으로 LangGraph 런타임을 사용하므로 둘 중 하나만 고르는 관계는 아니다. 단순한 공시 질의응답은 LangChain의 고수준 에이전트로 빠르게 만들고, 투자·검증·승인·실행처럼 통제가 필요한 전체 흐름은 LangGraph의 상태 그래프로 직접 정의한다.

### LangGraph가 필요한 이유

이 프로젝트에는 다음과 같은 상태 기반 흐름이 존재한다.

- 투자 에이전트와 검증 에이전트가 합의할 때까지 제한적으로 반복
- 검증 실패 시 실행 에이전트로 넘어가지 않는 조건부 분기
- 고액 주문이나 합의 실패 시 사용자 승인을 기다리는 중단
- 승인 후 중단 지점부터 안전하게 재개
- API 장애 후 완료된 분석을 다시 수행하지 않고 마지막 체크포인트부터 복구
- 판단·검증·승인·주문 상태를 하나의 실행 ID로 추적

LangGraph는 상태를 체크포인트로 저장하는 영속 실행과 human-in-the-loop 중단·재개를 지원하므로 이 구조와 잘 맞는다.

### 그래프 노드 초안

```text
START
  ↓
collect_data
  ↓
calculate_metrics
  ↓
investment_agent
  ↓
verification_agent
  ↓
┌──────────────────────────────────────┐
│ 승인 → policy_check                 │
│ 수정 → investment_agent로 재진입    │
│ 반려 → END                          │
│ 합의 실패 → human_interrupt          │
└──────────────────────────────────────┘
  ↓
policy_check
  ↓
┌──────────────────────────────────────┐
│ 자동 허용 → execution_agent          │
│ 승인 필요 → human_interrupt          │
│ 금지 → END                          │
└──────────────────────────────────────┘
  ↓
execution_agent
  ↓
reconcile_execution
  ↓
update_portfolio
  ↓
generate_report
  ↓
END
```

### 공유 상태 예시

```python
class InvestmentState(TypedDict):
    run_id: str
    user_policy_id: str
    market_as_of: str
    evidence_ids: list[str]
    proposal: dict | None
    verification: dict | None
    revision_count: int
    approval: dict | None
    order_request: dict | None
    execution_result: dict | None
    errors: list[dict]
```

공유 상태에는 API 비밀키, 계좌 비밀번호, 주민등록번호를 넣지 않는다. 실행 노드는 별도 보안 저장소에서 짧은 수명의 권한을 받아 금융 API를 호출한다.

### 도입 범위

1. **MVP:** LangGraph로 분석 → 검증 → 승인 분기 → 모의주문 흐름 구현
2. **고도화:** PostgreSQL 기반 체크포인트와 재시작 복구
3. **운영:** 실행 추적, 재시도, 타임아웃, 사용자별 동시 작업 제한
4. **평가:** 각 노드의 정확도·비용·지연시간과 검증 전후 오류 감소 측정

LangGraph가 증권사 주문의 안전성을 대신 보장하지는 않는다. 주문 멱등성, 권한 검사, 한도, 체결 확인은 기존 백엔드의 정책·실행 서비스에서 결정적으로 구현하고 LangGraph는 그 순서를 조정한다.

### 기본 원칙

처음부터 금융 LLM을 새로 사전학습하지 않는다. 팀 프로젝트의 핵심은 언어모델의 금융 상식 암기가 아니라 **최신 원문 조회, 정확한 계산, 행동 정책, 독립 검증**이다. 다음 네 층을 분리한다.

```text
LLM 에이전트: 자료 탐색, 가설, 설명, 반박
RAG: 공시·뉴스·정책·사용자 투자정책 검색
정형 계산 엔진: 재무비율·손익·위험·주문 수량 계산
정책 엔진: 한도·승인 등급·실행 가능 여부 결정
```

금액, 수익률, PER, 최대 낙폭 같은 값은 LLM이 머릿속으로 계산하게 하지 않고 코드로 계산한다. LLM은 계산 도구를 호출하고 결과를 해석한다.

### 1단계: 학습 없이 베이스라인 구축

1. OpenDART 문서를 기업·보고서·기간·표·계정 단위로 정규화한다.
2. 문단과 표에 접수번호, 기준일, 연결/별도 구분을 메타데이터로 붙인다.
3. 사용자의 질문과 투자안에 필요한 원문만 RAG로 검색한다.
4. 투자 제안과 검증 결과는 자유문장이 아니라 JSON 스키마로 출력한다.
5. 재무비율과 위험 지표는 Python 계산 함수가 만들고 단위 테스트로 검증한다.

이 단계만으로도 충분한 MVP가 가능하며, 학습 데이터가 부족한 초기에 미세조정을 서두르는 것보다 오류 원인을 추적하기 쉽다.

### 2단계: 지도학습용 데이터셋 구축

과거 시점별로 다음 한 묶음을 생성한다.

```text
시점 t까지 공개된 공시·가격·거시 데이터
사용자 위험 정책
투자 에이전트의 구조화된 제안
검증 에이전트가 찾아야 할 오류 라벨
전문가 또는 팀이 작성한 수정안
이후 기간의 실제 결과(학습 정답이 아닌 사후 평가용)
```

오류 라벨은 `숫자 오류`, `단위 오류`, `기준기간 오류`, `출처 불일치`, `최신 공시 누락`, `계산 오류`, `위험 한도 위반`, `근거 부족`, `과도한 확신` 등으로 만든다.

### 3단계: 필요한 모델만 미세조정

- **문서 분류·추출 모델:** 공시 문단의 위험요인, 실적 원인, 일회성 항목 분류
- **검증 분류 모델:** 주장과 인용문이 일치하는지, 오류 유형이 무엇인지 판정
- **LLM SFT:** 좋은 투자 제안서와 검증 보고서의 형식·질의 패턴 학습
- **랭킹 모델:** 동일 투자안에 대한 여러 반박 중 중요한 위험을 우선 정렬

대규모 언어모델 전체를 학습하기보다 작은 인코더 모델 또는 LoRA 방식의 제한된 미세조정을 우선한다. 미래 수익률만을 정답으로 삼아 LLM을 학습시키면 우연한 시장 결과를 올바른 논리로 착각할 수 있으므로 피한다.

### 4단계: 시계열·포트폴리오 모델

수익률 예측은 별도 정량 모델로 다룬다.

- 가격·거래량·재무 팩터 모델: LightGBM/XGBoost 베이스라인
- 위험 추정: 변동성, VaR/CVaR, 상관관계 및 최대 낙폭
- 비중 결정: 제약조건이 있는 평균-분산, 리스크 패리티 또는 규칙 기반 모델
- 시장 국면 분류: 금리·변동성·추세를 이용한 상태 모델

강화학습은 거래비용과 시장 변화에 과적합하기 쉬우므로 마지막 연구 단계로 미룬다. 먼저 단순 전략과 워크포워드 테스트를 통과해야 한다.

### 검증 에이전트의 독립성 확보

- 투자 에이전트의 내부 추론 전체가 아니라 `제안·근거·인용`만 전달한다.
- 원문을 별도로 다시 검색하고 계산도 별도 함수로 재실행한다.
- 가능하면 투자 에이전트와 다른 프롬프트·검색 쿼리·모델을 사용한다.
- 일부 평가에서는 정답을 숨긴 오류 주입 데이터로 탐지율을 측정한다.
- 두 에이전트가 같은 잘못된 데이터 공급자를 신뢰하지 않도록 공시·시세 출처를 교차 확인한다.

### 학습·평가 데이터 누수 방지

- 각 백테스트 시점 이후 발표된 공시와 수정공시를 차단한다.
- 생존 종목만 남기는 생존편향을 막기 위해 상장폐지 종목도 포함한다.
- 학습·검증·테스트를 무작위 행이 아니라 시간 순서로 분리한다.
- 거래비용, 세금, 슬리피지와 주문 미체결을 반영한다.
- 수익률 외에 오류 탐지율, 위험 한도 위반률, 근거 정확도도 함께 평가한다.

## 실행 안전장치

첫 버전은 실제 자금을 운용하지 않고 과거 데이터 백테스트와 실시간 시세 기반 모의투자로 개발한다.

- 데이터 시점 이후의 정보를 보지 못하게 하는 시점 통제
- 거래비용, 세금, 슬리피지를 포함한 성과 계산
- 종목·산업별 최대 비중 및 최대 손실 한도
- 검증 미통과 시 주문 차단
- 모든 판단, 반박, 수정, 승인 과정의 감사 로그 저장
- 긴급 중단 기능과 사용자 최종 승인
- 실행 에이전트의 최소 권한 및 계좌별 허용 작업 제한
- API 장애 시 재주문보다 거래 상태 조회를 먼저 수행해 중복 실행 방지

실제 주문 연동은 모의투자에서 기준 성과와 안전성을 확인한 이후의 별도 확장 단계로 둔다. 프로젝트의 목표는 수익 보장이 아니라 **투자 판단의 근거성, 검증 가능성, 위험 통제 능력**을 평가하는 것이다.

## 단계별 개발 범위

### 1단계: 분석과 검증

- 국내 상장기업 5~10개로 범위 제한
- 공시·재무제표 기반 투자안 생성
- 검증 에이전트의 수치·출처·논리 감사
- 두 에이전트의 질의응답과 수정 이력 표시

### 2단계: 모의투자

- 투자 정책과 위험 한도 설정
- 검증 결과에 따른 모의주문 실행
- 벤치마크 대비 성과와 최대 낙폭 측정
- 잘못된 투자 판단의 원인 분석

### 3단계: 사용자 개입

- 합의 실패 탐지
- 사용자 질문과 승인 UI
- 선택 결과를 이후 판단 정책에 반영

### 4단계: 실행 에이전트

- 증권사 모의투자 API 연동
- 자동 실행·간편 승인·강화 승인 정책 구현
- 주문 상태 추적과 중복 실행 방지
- 실행 전후 검증 및 감사 로그 구현

### 5단계: 통합 대시보드

- 보유자산, 원금, 평가금액 및 실현·미실현손익 통합
- 기간별 성과와 벤치마크 비교
- 기업 재무지표 추이 및 원문 근거 연결
- AI 판단·검증·승인·실행 이력 시각화
- 위험 알림과 향후 주요 일정 표시

### 6단계: 투자 리포트와 폐쇄 루프

- 주간·월간·분기 투자 리포트 자동 생성
- 검증 에이전트의 리포트 수치·출처·성과 귀인 감사
- 과거 판단과 실제 결과 비교
- 사용자 피드백을 다음 투자 정책에 반영
- 웹 리포트 및 PDF 내보내기

### 7단계: 자산군 확장

- ETF 및 채권 분석
- 실제 증권사 API는 별도의 안전성·규제 검토 후 선택적으로 연동

## 평가 지표

- 재무 수치 검증 정확도
- 잘못된 출처 및 근거 없는 주장 탐지율
- 검증 전후 투자안 오류 감소율
- 에이전트 합의율과 사용자 개입 빈도
- 모의투자 수익률, 변동성, 최대 낙폭
- 벤치마크 및 단일 에이전트 대비 성과
- 한 번의 투자 판단을 설명하는 데 필요한 근거 추적 가능성
- 손익과 원금의 계산 정확도 및 증권사 잔고 일치율
- 대시보드 정보의 기준 시각과 출처 표시 완전성

## 현재 핵심 가설

> 독립된 검증 에이전트가 투자 에이전트의 판단을 반박하고 수정하게 하면, 단일 금융 AI보다 수치 오류·근거 없는 판단·과도한 위험 행동을 줄일 수 있다.

이 가설은 동일 데이터와 동일 투자 기간을 사용해 `단일 투자 에이전트`와 `투자+검증 에이전트`의 결과를 비교하여 검증한다.
