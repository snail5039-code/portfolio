# 결정 데이터 통합 (1차)

기준일: 2026-09-01 KST

## 배경: 실제로 확인된 문제

`BACKEND-005`로 승인 대기에 쓰기 경로가 생긴 뒤, 결정(DEC) 데이터가 여러 화면 fixture에 각자 따로 있다는 문제가 실제로 드러났다.

- **DEC-1042**(삼성전자 매수)는 `dashboard.py`, `approvals.py`, `agents.py` 세 곳에 각자 리터럴로 있었다. 승인 대기에서 승인해도 대시보드의 "현재 판단" 패널은 항상 `조건부 승인 후보`로 고정 표시됐다 — 같은 결정인데 화면마다 다른 상태를 보여주는 버그였다.
- **DEC-1043**은 더 심각했다. 승인 대기에서는 "NAVER 매도 8주 대기중"인데, 검증 에이전트 화면에서는 같은 ID로 "NAVER 관찰 유지, 반려됨"이라고 **정반대** 내용을 보여주고 있었다. 두 화면을 교차 확인 없이 각자 만들면서 생긴 우연한 ID 충돌이었다.

이 문서는 이 두 문제를 고친 범위와, 고치지 않은 범위를 정확히 구분해 남긴다.

## 고친 것

### 1. DEC-1042 정적 사실을 한 곳으로

`app/fixtures/decisions.py`에 `DecisionFacts` 데이터클래스로 `DEC_1042`(회사, 코드, 매매 구분, 수량, 가격)를 정의했다. `amount`는 `quantity * price` 계산 프로퍼티라 두 숫자가 있으면 금액은 항상 맞는다.

`dashboard.py`와 `approvals.py`의 DEC-1042 항목이 이 상수를 참조한다. 가격이나 수량을 바꾸려면 이제 한 곳만 고치면 되고, 두 화면이 서로 다른 숫자를 보여줄 방법이 없다.

**의도적으로 옮기지 않은 것**: 근거 문구, 경고 문구, 무효 조건 같은 화면별 산문(prose)은 그대로 각 파일에 남겼다. `invalidConditions`의 "지정가가 71,200원을 초과할 때" 같은 문장 속 숫자는 상수와 자동으로 맞물리지 않는다. 모든 한글 문장을 템플릿화하는 건 과도한 엔지니어링이라 판단했고, 대신 이 사실을 여기 명시해 다음에 가격을 바꾸는 사람이 그 문장도 함께 확인하게 남긴다.

### 2. DEC-1042 살아있는 상태를 승인 대기와 공유

가장 실질적인 수정이다. `app/schemas/common.py`에 `DecisionStatus = Literal["pending", "approved", "rejected"]`를 한 번만 정의하고 `dashboard.py`와 `approvals.py` 스키마가 같이 가져다 쓴다.

`GET /api/dashboard`는 이제 `Request`를 받아 `request.app.state.approval_store.get("DEC-1042")`로 **같은 스토어**를 조회하고, 그 결과를 `DashboardDecision.decisionStatus`/`decidedAt`에 얹는다. `build_dashboard_data()`는 `decision_status`/`decided_at` 매개변수를 받고, 기본값 `"pending"`/`None`이라 기존 테스트나 다른 호출자는 그대로 동작한다.

결과: 승인 대기에서 DEC-1042를 승인하면 대시보드도 새로고침 없이 같은 상태를 보여준다. 반대로 대시보드의 승인 패널에서 승인해도 승인 대기 화면이 같은 상태를 보여준다 — 둘 다 같은 백엔드 액션(`POST /api/approvals/DEC-1042/approve`)을 부르기 때문이다.

### 3. 대시보드의 가짜 승인 버튼을 실제 API로 교체

`DashboardPage`의 「반려」·「모의승인」 버튼은 지금까지 로컬 문자열만 바꾸는 **완전히 가짜인 두 번째 승인 UI**였다. 승인 대기 화면과 별개로 존재해서, 사용자가 대시보드에서 "승인"을 누르고 승인 대기 화면에 가면 여전히 대기 중으로 보이는 모순이 가능했다.

이제 `src/api/approvals.ts`의 `approveOrder`/`rejectOrder`를 그대로 재사용한다. 두 화면 다 같은 엔드포인트로 수렴하므로 "두 UI가 같은 결정에 대해 서로 다른 답을 준다"는 경우가 구조적으로 없다. 결정된 뒤에는 버튼이 비활성화되고 실제 결정 시각이 표시된다.

### 4. DEC-1043 ID 충돌 해소

`agents.py`의 NAVER "관찰 유지" 예시(분석·검증·실행 세 항목)를 `DEC-1043`에서 **`DEC-1057`**로 옮겼다. 1057은 현재 어떤 화면에서도 쓰이지 않는 번호다. 승인 대기의 진짜 `DEC-1043`(NAVER 매도 주문)과 더 이상 같은 ID를 공유하지 않는다.

관련 항목 ID(`AN-1043`→`AN-1057`, `VF-1043`→`VF-1057`, `EX-1043`→`EX-1057`)와 실행 화면의 "DEC-1043 · 반려 수신" 문구도 함께 갱신했다.

### 5. 교차 검증 테스트

`test_dashboard.py`에 다섯 개를 추가했다. 핵심은 이거다.

```python
def test_approving_the_decision_via_approvals_is_reflected_on_dashboard() -> None:
    client = TestClient(create_app())
    client.post("/api/approvals/DEC-1042/approve")
    dashboard = client.get("/api/dashboard").json()["data"]["decision"]
    assert dashboard["decisionStatus"] == "approved"
```

같은 앱 인스턴스에서 승인 대기로 승인하고, 대시보드가 그걸 보여주는지 확인한다. 이 테스트가 지금 이 문서가 고쳤다고 주장하는 것의 유일한 증거다.

## 고치지 않은 것 — 다음 범위

**16개 결정 ID 전체를 통합하지 않았다.** 나머지 12개 프론트엔드 fixture 파일(감사 로그, 결정 회고, 근거 패킷, 정책 설정, 포트폴리오 건강, 리스크 알림, 거래 내역, 투자 리포트, 역할 상태 등)은 여전히 각자 결정 데이터를 따로 들고 있고, 백엔드에 연결되지도 않았다. DEC-1042를 승인해도 이 화면들은 갱신되지 않는다.

이번 범위를 여기로 좁힌 이유:

- 실제로 desync가 **관찰 가능한** 지점은 backend가 연결된 화면끼리(대시보드·승인 대기·에이전트)뿐이었다. 나머지는 애초에 살아있는 상태가 없는 정적 화면이라 "따로 논다"는 게 지금 당장 사용자에게 보이는 버그가 아니다.
- 12개 화면을 전부 백엔드로 옮기는 건 사실상 남은 풀스택 전환 로드맵 전체(Phase 3 이후)를 이 한 작업에서 다 하는 것과 같다. 별도로 승인받을 범위다.

DEC-1052(SK하이닉스)는 검사했고 화면 간 서사가 대체로 일치해 손대지 않았다. 다른 12개 ID는 개별 대조를 다 하지 않았다 — 이 문서가 "16개 다 확인했다"고 주장하지 않는 이유다.
