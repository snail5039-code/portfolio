# Skill Harvester 제품 기획서

> 사용자가 만족한 AI 작업을 검증 가능한 재사용 스킬로 전환하는 개인 업무 학습 시스템

## 1. 문서 정보

- 문서 상태: 아이디어 검증용 초안
- 작성일: 2026-08-25
- 프로젝트 가칭: **Skill Harvester**
- 핵심 문구: **“완벽해”라고 말한 작업을 다음에도 같은 품질로.**
- 현재 범위: 제품 개념, 사용자 흐름, 기능 요구사항, 안전장치, MVP 및 검증 계획
- 지원 목표: OpenAI Codex와 Anthropic Claude Code
- 제외 범위: 실제 플러그인 구현, 외부 배포, 결제, 사용자 데이터 수집

## 2. 한 줄 정의

사용자가 AI 에이전트의 작업 결과를 만족스럽다고 승인하면, 성공 과정에서 반복 가능한 업무 방법을 추출하고 검증하여 이후 유사 작업에 재사용할 수 있는 **플랫폼 중립적인 개인 또는 팀 스킬**로 만드는 시스템이다. 하나의 공통 스킬 원본에서 Codex와 Claude Code용 설치 패키지를 생성한다.

## 3. 문제 정의

AI 에이전트는 프로젝트와 반복 업무를 해결할 수 있지만, 성공한 작업 방식이 대화 종료 후 재사용 가능한 절차로 남지 않는 경우가 많다.

사용자는 반복 작업에서 다음 비용을 다시 지불한다.

- 이전 요구사항과 선호도를 다시 설명한다.
- 에이전트가 같은 파일과 자료를 다시 탐색한다.
- 과거에 실패했던 접근을 다시 시도한다.
- 원하는 결과 형식과 검증 기준을 반복해서 알려준다.
- 이전 대화나 문서를 찾아 “지난번처럼” 처리해 달라고 요청한다.

기존 메모리는 주로 사실과 대화 내용을 저장한다. 본 제품은 사실이 아니라 **검증된 일하는 방법**을 저장하는 것을 목표로 한다.

## 4. 제품 가설

### 핵심 가설

사용자가 성공을 확인한 AI 작업에서 일반화 가능한 절차를 추출하고, 유사하지만 다른 사례로 검증한 후 스킬로 저장하면 반복 작업의 설명 비용, 탐색 시간과 토큰 사용량을 줄이면서 결과의 일관성을 높일 수 있다.

### 가치 가설

- 사용자는 스킬 작성법이나 `SKILL.md` 형식을 몰라도 된다.
- 만족한 작업을 승인하는 자연스러운 행동만으로 자동화 후보를 만들 수 있다.
- 실제 성공 사례에서 출발하므로 사전에 설계한 자동화보다 사용자의 업무 방식에 가깝다.
- 스킬이 반복 사용될수록 개인과 팀의 업무 지식이 축적된다.

### 검증이 필요한 가정

- 사용자의 만족 표현이 실제 작업 성공을 충분히 의미하는가?
- 한 작업의 성공 경로를 다른 유사 작업에 일반화할 수 있는가?
- 스킬 적용이 품질 저하 없이 시간과 토큰을 줄이는가?
- 사용자가 스킬 후보 검토와 저장 절차를 번거롭게 느끼지 않는가?
- 스킬이 많아져도 올바른 스킬을 안정적으로 선택할 수 있는가?

## 5. 대상 사용자

### 1차 대상

- AI 코딩 에이전트로 반복적인 개발·검토·문서화 작업을 수행하는 개인 개발자
- Codex와 Claude Code를 함께 사용하거나 도구를 전환하는 사용자
- 프로젝트별 규칙과 검증 절차를 반복해서 설명하는 사용자
- 스킬을 직접 작성할 기술은 없지만 반복 업무를 자동화하고 싶은 사용자

### 확장 대상

- 주간 보고서, 회의록, 데이터 정리, 고객 응대 등 반복 업무를 수행하는 일반 사용자
- 팀 표준 작업법을 유지하려는 개발팀과 운영팀
- 성공한 업무 절차를 조직 자산으로 축적하려는 기업

## 6. 대표 사용 사례

### 개발

- 반복되는 인증·세션 오류 진단
- 코드 리뷰 기준 적용
- 프로젝트 생성 및 초기 설정
- 배포 전 검증
- 특정 유형의 회귀 버그 수정

### 사무 및 콘텐츠

- 매주 동일한 형식의 보고서 작성
- 회의록에서 결정과 후속 작업 추출
- CSV 및 스프레드시트 정제
- 브랜드 규칙에 맞는 콘텐츠 작성
- 고객 문의 분류 및 답변 초안 생성

## 7. 핵심 사용자 경험

### 기본 흐름

```text
사용자 요청
  → AI가 작업 수행 및 검증
  → 사용자가 결과 만족을 확인
  → 시스템이 재사용 가능성을 판단
  → 스킬 후보를 쉬운 말로 설명
  → 사용자 승인
  → 개인정보 및 일회성 정보 제거
  → 유사 사례 검증
  → 개인 스킬로 저장
  → 이후 유사 작업에서 적용 제안
```

### 사용자 대화 예시

```text
사용자: 완벽해. 다음에도 이렇게 해줘.

AI: 이번 작업에서 반복 가능한 방법을 발견했습니다.

후보: 인증 토큰 만료 오류 진단
- 시간 단위 혼용 확인
- 만료 경계값 테스트
- 서버와 클라이언트 시간 차이 확인

이번 프로젝트의 경로, 실제 토큰 값과 개인정보는 저장하지 않습니다.
이 방법을 개인 스킬로 만들까요?

[스킬 만들기] [내용 확인] [이번만 사용]
```

### 재사용 흐름

```text
AI: 저장된 ‘인증 토큰 만료 오류 진단’ 방법과 유사한 작업입니다.
적용해도 될까요?

[적용] [이번만 적용하지 않음] [스킬 내용 보기]
```

충분한 신뢰가 쌓이기 전에는 자동 적용보다 적용 제안을 기본값으로 한다.

## 8. 기능 요구사항

### 8.1 성공 신호 감지

- “완벽해”, “해결됐어”, “다음에도 이렇게 해줘”와 같은 명시적 성공 표현을 감지한다.
- 테스트 통과, 산출물 존재, 오류 해소 등 관찰 가능한 완료 증거를 함께 확인한다.
- 칭찬이나 감사 표현만으로 영구 저장하지 않는다.
- 작업 성공 승인을 스킬 설치 승인으로 간주하지 않는다.

### 8.2 성공 과정 분석

- 최종 해결에 기여한 행동과 근거를 추출한다.
- 실패한 가설과 불필요한 시행착오는 기본적으로 제외한다.
- 문제 조건, 진단 방법, 해결 기준과 검증 방법을 구분한다.
- 성공 원인을 설명할 근거가 부족하면 스킬 생성을 보류한다.

### 8.3 일반화

다음 두 범주를 분리한다.

**보존 대상**

- 적용 조건
- 문제를 좁히는 순서
- 해결책 선택 기준
- 반드시 확인해야 하는 예외
- 품질 및 안전 조건
- 완료와 검증 기준
- 실패 시 조사 범위를 확대하는 조건

**제거 또는 변수화 대상**

- 사용자 및 조직의 개인정보
- 비밀키, 토큰, 계정정보
- 특정 실행에서 사용한 실제 데이터
- 절대 파일 경로
- 특정 프로젝트에만 존재하는 이름
- 우연히 성공했지만 원인이 확인되지 않은 행동
- 사용자의 일회성 선택

### 8.4 스킬 가치 판정

다음 질문 중 하나 이상을 만족하지 못하면 새 스킬을 만들지 않는다.

- 동일하거나 유사한 작업이 반복될 가능성이 있는가?
- 일반 모델 능력 이상의 고유한 절차 또는 기준이 있는가?
- 다른 사례에도 적용 가능한가?
- 성공 여부를 검증할 수 있는가?
- 짧은 일회성 프롬프트보다 재사용 가치가 있는가?

### 8.5 중복 및 충돌 검사

- 설치된 스킬과 이름, 설명, 적용 조건 및 절차를 비교한다.
- 기존 스킬에 이미 포함된 방법이면 새로 만들지 않는다.
- 일부만 새로운 경우 기존 스킬의 업데이트 후보로 제안한다.
- 서로 충돌하는 스킬이 있으면 사용자에게 차이를 설명한다.
- 자동 호출 설명이 지나치게 넓어지지 않도록 제한한다.

### 8.6 스킬 후보 생성

각 후보는 최소한 다음 내용을 가진다.

- 이름
- 짧고 구별 가능한 설명
- 적용해야 하는 상황
- 적용하지 않아야 하는 상황
- 핵심 작업 흐름
- 안전 및 품질 조건
- 완료 기준
- 필요한 경우에만 읽는 참고자료 또는 실행 스크립트
- 원본 성공 사례와 생성 근거를 가리키는 내부 메타데이터

`SKILL.md`는 짧게 유지하고, 조건부 상세 내용은 `references/`, 반복적이고 결정론적인 처리는 `scripts/`로 분리한다.

### 8.6.1 플랫폼 중립 스킬 원본

- 공통 원본은 Agent Skills 공개 사양의 필수 구조를 따른다.
- 공통 `SKILL.md`의 필수 frontmatter는 `name`과 `description`으로 제한한다.
- 플랫폼별 전용 설정을 공통 본문에 섞지 않는다.
- 파일 참조는 스킬 루트를 기준으로 한 상대 경로를 사용한다.
- 스크립트는 가능한 경우 Windows, macOS와 Linux에서 실행 가능하게 작성한다.
- 특정 플랫폼이나 도구가 반드시 필요하면 `compatibility`에 명시한다.

### 8.6.2 Codex 어댑터

- 공통 스킬 원본을 Codex가 검색할 수 있는 개인 또는 프로젝트 스킬 위치에 설치한다.
- 필요한 경우 `agents/openai.yaml`을 생성하여 표시 이름, 설명과 호출 정책을 제공한다.
- 자동 호출 여부와 외부 변경 승인 규칙을 Codex 정책에 맞게 보존한다.
- Codex 전용 파일은 생성물로 취급하고 공통 `SKILL.md`를 원본으로 유지한다.

### 8.6.3 Claude Code 어댑터

- 프로젝트 스킬은 `.claude/skills/<skill-name>/SKILL.md` 구조로 내보낸다.
- 배포용 플러그인은 `skills/<skill-name>/SKILL.md` 아래에 공통 원본을 포함한다.
- 필요 시 Claude Code 전용 frontmatter인 `disable-model-invocation`, `user-invocable`, `allowed-tools`, `context`, `agent`를 별도 어댑터 설정에서 생성한다.
- 후크가 필요한 기능은 사용자 승인 후 별도 Claude 플러그인 구성으로 제공하며, 공통 스킬이 후크 존재를 전제로 하지 않도록 한다.

### 8.6.4 단일 원본 원칙

```text
canonical/SKILL.md
        ├─ Codex 패키지 생성
        └─ Claude Code 패키지 생성
```

- 사람이 직접 수정하는 원본은 하나만 둔다.
- 플랫폼별 복사본을 직접 편집하지 않는다.
- 생성 스크립트에 `--check` 모드를 제공하여 복사본 불일치를 CI에서 탐지한다.
- 두 플랫폼이 공통으로 이해하지 못하는 필드는 어댑터 설정에만 저장한다.

### 8.7 검증

- 원래 작업을 그대로 재실행하는 것만으로 통과시키지 않는다.
- 유사하지만 다른 변형 과제를 사용한다.
- 스킬 미사용 기준선과 스킬 사용 결과를 비교한다.
- 품질 기준을 통과한 결과에 한해서만 토큰·시간 절감 효과를 평가한다.
- 검증 실패 시 설치하지 않고 원인과 수정 후보를 보고한다.

### 8.8 승인 및 설치

- 사용자 승인 전에는 영구 스킬을 만들거나 설치하지 않는다.
- 생성될 파일, 저장 정보와 제외 정보를 쉬운 말로 보여준다.
- 설치 전 기존 버전을 보존한다.
- 되돌리기와 비활성화를 지원한다.
- 사용자는 개별 스킬을 열람, 수정, 비활성화 및 삭제할 수 있다.

### 8.9 사용 후 학습

- 스킬 적용 여부와 결과를 기록한다.
- 성공, 실패, 사용자 수정과 적용 거절을 구분한다.
- 한 번의 실패로 즉시 일반 규칙을 변경하지 않는다.
- 반복된 증거가 있을 때 업데이트 후보를 제안한다.
- 오래 사용되지 않거나 효과가 없는 스킬은 제거가 아닌 비활성화 후보로 먼저 제안한다.

## 9. 품질 및 안전 원칙

1. **사용자 의도 우선:** 스킬이 현재 요청을 대신하거나 범위를 확대해서는 안 된다.
2. **품질 우선:** 토큰과 시간 절약 때문에 요구사항, 검증, 보안 또는 정확성을 희생하지 않는다.
3. **승인 분리:** 결과 승인, 스킬 생성 승인, 외부 공유 승인을 서로 분리한다.
4. **최소 저장:** 재사용에 필요한 정보만 저장한다.
5. **출처 추적:** 스킬이 어떤 성공 사례와 증거에서 만들어졌는지 기록한다.
6. **가역성:** 업데이트, 비활성화와 삭제 전에 복구 가능한 버전을 보존한다.
7. **불확실성 공개:** 검증하지 못한 일반화는 사실처럼 저장하지 않는다.
8. **과잉 학습 방지:** 하나의 프로젝트 경로나 변수명을 보편적인 규칙으로 만들지 않는다.

## 10. 스킬 생성 판정 예시

### 생성 가치가 낮은 사례

- 단순 오탈자 수정
- 파일명 변경 한 번
- 일반 모델이 이미 안정적으로 수행하는 한 단계 작업
- 성공 원인을 확인할 수 없는 우연한 해결

### 생성 가치가 높은 사례

- 반복되는 인증 오류의 진단과 경계값 검증

- 같은 입력 형식에서 반복되는 데이터 정제 및 보고서 생성
- 팀의 코드 리뷰 기준과 재현 절차
- 프로젝트별 접근성, 보안 및 호환성 검증 과정

## 12. MVP 범위

### MVP 목표

Codex 또는 Claude Code에서 완료된 한 개의 작업 기록을 바탕으로 플랫폼 중립적인 스킬 후보 보고서와 `SKILL.md` 초안을 생성한다. 승인된 후보는 동일한 공통 원본에서 Codex와 Claude Code용 패키지로 내보낼 수 있어야 하며, 사용자 승인 전에는 어느 환경에도 설치하지 않는다.

### 포함 기능

- 사용자가 명시적으로 성공한 현재 작업 분석
- 재사용 가치 판정
- 일반화 가능한 절차 추출
- 민감정보 및 프로젝트 전용 정보 후보 탐지
- 기존 로컬 스킬과 기본 중복 검사
- 스킬 후보 미리보기
- 사용자 승인 후 개인 스킬 폴더에 생성
- 공통 Agent Skills 형식 검증
- Codex용 패키지 생성 및 구조 검증
- Claude Code용 패키지 생성 및 구조 검증
- 플랫폼별 설치 위치를 보여주는 미리보기와 선택 설치
- 생성 전후 파일 차이와 복구 방법 보고

### MVP 제외 기능

- 사용자 몰래 자동 생성 및 자동 설치
- 클라우드 동기화
- 팀 공유 및 공개 마켓 등록
- 모든 종류의 개인정보 자동 판별 보장
- 스킬의 자동 영구 삭제
- 모델별 완전 자동 최적화
- 장기간 사용 통계 기반 자동 업데이트

## 13. 구현 구성 초안

```text
skill-harvester/
├─ SKILL.md
├─ agents/
│  └─ openai.yaml
├─ scripts/
│  ├─ extract_candidate.py
│  ├─ redact_context.py
│  ├─ compare_skills.py
│  ├─ build_skill.py
│  ├─ build_codex_adapter.py
│  ├─ build_claude_adapter.py
│  └─ validate_candidate.py
└─ references/
   ├─ generalization-rules.md
   ├─ privacy-rules.md
   ├─ platform-compatibility.md
   └─ evaluation-protocol.md
```

구현 시 실제 필요성이 확인된 파일만 생성한다. 초기 버전에서는 단일 `SKILL.md`와 최소 스크립트로 시작할 수 있다.

### 생성되는 스킬 패키지 구조

```text
generated/<skill-name>/
├─ canonical/
│  ├─ SKILL.md
│  ├─ scripts/
│  ├─ references/
│  └─ assets/
├─ codex/
│  ├─ SKILL.md
│  ├─ agents/openai.yaml
│  └─ 공통 리소스
├─ claude-code/
│  ├─ SKILL.md
│  └─ 공통 리소스
└─ manifest.json
```

`manifest.json`에는 원본 해시, 생성기 버전, 대상 플랫폼, 검증 결과와 설치 이력을 기록한다. 비밀정보와 실제 작업 데이터는 포함하지 않는다.

### 플랫폼 호환성 원칙

| 항목 | 공통 원본 | Codex | Claude Code |
|---|---|---|---|
| `SKILL.md` | 필수 | 사용 | 사용 |
| `name`, `description` | 필수 | 사용 | 사용 |
| `scripts/`, `references/`, `assets/` | 선택 | 사용 | 사용 |
| UI 메타데이터 | 제외 | `agents/openai.yaml` | 플러그인 메타데이터 |
| 호출 제어 | 중립적 기본값 | Codex 정책 어댑터 | Claude 전용 frontmatter |
| 후크 | 제외 | 필요 시 별도 플러그인 | 필요 시 Claude hooks |
| 설치 | 대상 아님 | Codex 개인/프로젝트 위치 | `.claude/skills/` 또는 플러그인 |

공통 기능은 두 플랫폼에서 동일한 결과를 목표로 하지만, 도구 이름과 권한 모델이 다를 수 있으므로 지침에는 특정 도구명을 강제하기보다 필요한 능력과 완료 조건을 기술한다.

## 14. 검증 계획

### 비교 조건

```text
A. 스킬 없음
B. “지난번처럼 처리”라는 짧은 프롬프트
C. 생성된 Skill Harvester 스킬 사용
```

### 고정 조건

- 동일한 모델과 모델 버전
- 동일한 reasoning 수준
- 동일한 저장소 커밋 또는 입력 데이터
- 동일한 도구와 권한
- 각 조건을 독립된 새 세션에서 실행
- 조건별 최소 3회 반복
- 개발에 사용하지 않은 holdout 과제 포함
- Codex와 Claude Code에서 각각 실행
- 플랫폼별로 지원되는 비교 가능한 모델과 도구 조건을 기록

### 품질 지표

- 요구사항 충족률
- 테스트 및 숨겨진 테스트 통과율
- 회귀 발생 여부
- 보안·입력 검증·접근성 보존 여부
- 사용자가 수정해야 하는 추가 작업량
- 잘못된 스킬 호출률
- 플랫폼 간 요구사항 충족률 차이
- 플랫폼 전용 지침 없이 공통 원본으로 완료한 비율

### 효율 지표

- 입력·출력·전체 처리 토큰
- 실행 시간
- 도구 호출 횟수
- 읽은 파일 및 줄 수
- 재시도 횟수
- 사용자 개입 횟수

### 통과 원칙

```text
요구사항 누락, 테스트 실패 또는 안전 조건 훼손
  → 토큰 절감과 관계없이 실패

품질 기준 통과
  → 이후에만 토큰, 시간 및 반복 작업 감소 평가
```

### 초기 성공 기준

- 유사 작업 품질이 기준선보다 실질적으로 악화되지 않는다.
- 중대 또는 높은 수준의 안전 회귀가 없다.
- 사용자가 스킬 후보의 목적과 저장 정보를 이해할 수 있다.
- 불필요한 스킬 생성률과 잘못된 자동 호출률을 측정할 수 있다.
- 품질 통과 사례에서 설명·탐색·처리 비용 중 하나 이상의 개선이 관찰된다.
- 동일한 공통 스킬이 Codex와 Claude Code 양쪽에서 형식 검증을 통과한다.
- 플랫폼 차이로 동작이 달라질 때 원인과 지원 범위를 명시할 수 있다.

구체적인 수치 기준은 파일럿 결과를 확인한 뒤 고정한다. 임의의 절감률을 사전에 성능 보장으로 제시하지 않는다.

## 15. 주요 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 한 번의 성공을 보편 규칙으로 저장 | 이후 작업 품질 저하 | 변형 과제와 holdout 검증 |
| 개인정보·비밀정보 저장 | 보안 및 신뢰 문제 | 최소 저장, 탐지, 미리보기와 승인 |
| 스킬 과다 생성 | 선택 비용 및 토큰 증가 | 가치 판정, 중복 검사, 비활성화 수명주기 |
| 잘못된 자동 호출 | 작업 범위 왜곡 | 명확한 설명, 제외 조건, 초기 적용 승인 |
| 기존 스킬과 충돌 | 결과 불안정 | 호출 조건 비교와 우선순위 표시 |
| 절약을 위한 품질 희생 | 사용자 신뢰 상실 | 품질 게이트 통과 후 효율 평가 |
| 프로젝트 지식을 과도하게 일반화 | 다른 환경에서 실패 | 고유 값 변수화, 적용 범위 명시 |
| 외부 스킬 문구·코드 복제 | 라이선스 위험 | 독립 구현, 출처 기록, 라이선스 준수 |
| 플랫폼별 복사본 불일치 | 한쪽에서만 오래된 동작 | 단일 원본 생성과 `--check` 검증 |
| Codex·Claude 도구 차이 | 동일 스킬의 실행 실패 | 능력 중심 지침과 플랫폼 어댑터 |
| 전용 frontmatter 혼합 | 다른 플랫폼에서 호환성 저하 | 공통 필드와 플랫폼 전용 설정 분리 |

## 16. 향후 확장

### Skill Evaluator

- 모델별 스킬 성능 비교
- 품질, 토큰, 비용 및 시간 측정
- 업데이트 전후 회귀 평가

### Skill Steward

- 중복·노후·저효율 스킬 진단
- 사용자 승인 기반 업데이트, 비활성화, 보관 및 삭제
- 버전 관리와 롤백

### Team Skill Library

- 개인 스킬을 팀 후보로 승격
- 리뷰 및 승인 워크플로
- 조직 정책과 프로젝트별 변형 관리

### Quality-Aware Context

- 성공률을 보존하며 필요한 정보만 선택
- 큰 도구 출력의 가역적 압축
- 불확실성 증가 시 조사 범위 자동 확대

## 17. 제품 차별점

일반적인 자동화 도구는 사용자가 먼저 절차를 설계해야 한다. Skill Harvester는 실제로 성공한 작업을 나중에 자동화한다.

```text
기존 방식: 절차 설계 → 자동화 → 실제 업무에서 검증
제안 방식: 실제 업무 성공 → 절차 추출 → 검증 → 자동화
```

핵심 차별점은 다음과 같다.

- 사용자가 스킬을 직접 작성할 필요가 없다.
- 성공한 실제 작업에서 출발한다.
- 사실이 아니라 일하는 방법을 기억한다.
- 원래 사례가 아닌 변형 사례에서 재사용 가능성을 검증한다.
- 사용자 승인과 복구 가능한 수명주기를 기본으로 한다.

## 18. 핵심 제품 원칙

> 먼저 잘 해결한다. 사용자가 만족한 방법만 후보로 만든다. 다른 문제에서도 통하는지 검증한다. 사용자가 승인한 능력만 기억한다.

## 19. 다음 의사결정

1. 프로젝트 가칭 `Skill Harvester`를 유지할지 결정한다.
