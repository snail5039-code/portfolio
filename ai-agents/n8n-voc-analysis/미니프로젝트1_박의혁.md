## 1. 프로젝트 개요

### 1-1. 목표
종합 쇼핑몰의 고객 문의(VOC, Voice of Customer)를 자동으로 분류하고 처리하여:
- **자동화**: 사람 손을 거치지 않는 파이프라인 구축
- **신속성**: 긴급 문의를 실시간으로 감지하고 알림
- **일관성**: 객관적이고 통일된 분류 기준 적용
- **효율성**: 담당자는 알림이 왔을 때만 개입

### 1-2. 기술 스택
| 구성요소 | 도구 | 역할 |
|---------|------|------|
| 수집 | Google Form | 고객 문의 입력 |
| 저장소 | Google Sheets | 원본 응답(폼응답) + 분석 결과(분석결과) 저장 |
| 자동화 | n8n | 중복 확인, LLM 분류, 검증, 저장, 알림 |
| AI 분류 | n8n AI Agent + Google Gemini Chat Model (`gemini-3.5-flash`) + Structured Output Parser | 감정분석, 긴급도 판정, 요약, 스키마 강제 |
| 알림 | Discord Webhook | 긴급 문의 실시간 알림 |

## 2. 전체 워크플로우 설명 (통합)

### 2-1. 시스템 아키텍처

```
[고객]
  │ 문의 작성
  ▼
Google Form ──제출──> Google Sheet (폼응답 시트)
                          │
                          ▼
                    ┌─────────────────┐
                    │      n8n        │
                    │                 │
                    │ 1. 중복 확인    │
                    │ 2. LLM 분류     │
                    │ 3. 검증 안전판  │
                    │ 4. 결과 저장    │
                    │ 5. 긴급 분기    │
                    └─────────────────┘
                       │        │
                긴급건만 │        │ 모든건
                       ▼        ▼
                  Discord    Google Sheet
                  채널 알림   (분석 결과 시트)
```

### 2-2. n8n 워크플로우 노드 구조 (9개 노드)

```
폼 제출 감지 (Trigger)
    ├──▶ 분석결과 전체 조회 (참조용, 막다른 가지)
    └──▶ 중복 여부 분기 (If)
              │false(신규)
              ▼
         AI 분류 (AI Agent)
              │  ├─ Chat Model: Google Gemini Chat Model
              │  └─ Output Parser: 분류 결과 스키마
              ▼
         최종 데이터 정리 (Edit Fields)
              ▼
         분석결과 저장 (Append Row)
              ▼
         긴급도 분기 (If)
              │true(상)
              ▼
         긴급 알림 발송 (Discord)
```

### 2-3. 파이프라인 동작 흐름

#### Step 1: 수집 (Google Form)
고객이 폼에 문의유형/문의내용/이메일/물품 번호 4개 필드를 입력해 제출하면, Google Form 응답 저장 기능을 통해 "폼응답" 시트에 자동으로 한 행이 추가된다.

#### Step 2: 트리거 (n8n)
n8n의 Google Sheets Trigger(`폼 제출 감지`)가 "폼응답" 시트를 폴링(Every Minute)하며 신규 행을 감지하는 즉시 워크플로우를 자동 실행한다. 수동 실행(Manual Trigger)만으로는 요구사항을 충족하지 못하므로, 자동 트리거 방식으로 구성했으며 워크플로우는 Published(Active) 상태를 유지한다.

#### Step 3: 중복 확인 (LLM 호출 전 차단)
`분석결과 전체 조회` 노드가 "분석결과" 시트를 필터 없이 **전체 조회**한다. `중복 여부 분기`(If) 노드가 아래 표현식으로 현재 들어온 문의의 **물품번호와 이메일 조합**이 전체 목록 안에 이미 존재하는지 직접 검사한다.

```
{{ $('분석결과 전체 조회').all().some(row =>
     row.json['물품번호'] == $json['물품 번호'] &&
     row.json['이메일'] == $json['이메일']
   ) }}
```

일치하는 행이 있으면(true) LLM을 호출하지 않고, 저장과 알림 없이 워크플로우를 정상 종료한다. 물품번호 하나만이 아니라 **물품번호+이메일 조합**으로 판정하기 때문에, 같은 상품에 대해 다른 고객이 새로 문의한 경우는 중복으로 오판되지 않는다.

> **설계 노트**: 처음에는 "필터가 걸린 Get Row(s) 노드 + Merge(Position)" 방식으로 중복확인을 구현했으나, 필터형 조회 노드가 여러 아이템을 동시에 받았을 때 아이템 수만큼 안정적으로 반복 실행되지 않는 현상(예: 입력 2개인데 출력 1개)이 실측으로 확인되어, Merge의 위치 기반 짝짓기가 깨지고 데이터가 유실되는 문제가 발생했다. 이를 근본적으로 해결하기 위해 **필터 없는 전체 조회 1회 + If 조건 내 배열 탐색(`.some()`)** 방식으로 재설계했으며, 이 방식은 아이템 개수·순서에 의존하지 않아 동시에 여러 건이 들어와도 유실 없이 안전하게 동작함을 다건 동시 제출 테스트로 검증했다.

#### Step 4: LLM 분류 (AI Agent + Google Gemini)
중복이 아닌 경우에만 `AI 분류`(AI Agent) 노드가 문의내용을 Google Gemini Chat Model(`gemini-3.5-flash`)에 전달한다. `분류 결과 스키마`(Structured Output Parser)가 아래 JSON 스키마로 응답 형식을 강제하며, 허용값(enum)을 벗어나면 자동으로 재시도한다.

```json
{
  "type": "object",
  "properties": {
    "category": { "type": "string", "enum": ["결제","계정","상품","배송","기타"] },
    "sentiment": { "type": "string", "enum": ["긍정","중립","부정"] },
    "urgency": { "type": "string", "enum": ["상","중","하"] },
    "summary": { "type": "string" },
    "needs_review": { "type": "boolean" }
  },
  "required": ["category","sentiment","urgency","summary","needs_review"]
}
```

**System Message(긴급도 판정 기준 포함):**
> 당신은 고객 문의 분류 전문가입니다. 다음 고객 문의를 읽고 JSON으로만 응답하세요. 응답 형식: category(결제|계정|상품|배송|기타), sentiment(긍정|중립|부정), urgency(상|중|하), summary(80자 이하 요약), needs_review(false). 긴급도 판정 기준: 상=서비스 불가/금전 피해/법적 대응이나 언론 제보 언급/명시적 환불 요구, 중=불편하지만 사용 가능한 문의와 개선 요청, 하=단순 질문/칭찬/정보 확인.

#### Step 5: 검증 안전판
`분류 결과 스키마`의 enum 강제가 1차 방어선이지만, 스키마 강제만으로는 REQ-05가 요구하는 "위반해도 워크플로우가 죽지 않고 기본값으로 안전하게 계속 진행"을 보장하지 못한다. 이를 위해 `최종 데이터 정리`(Edit Fields) 노드에서 **Code 노드 없이 표현식만으로** 2차 안전판을 구현했다.

```
category      : {{ ['결제','계정','상품','배송','기타'].includes($json.output?.category) ? $json.output.category : '기타' }}
sentiment     : {{ ['긍정','중립','부정'].includes($json.output?.sentiment) ? $json.output.sentiment : '중립' }}
urgency       : {{ ['상','중','하'].includes($json.output?.urgency) ? $json.output.urgency : '중' }}
summary       : {{ ($json.output?.summary || '').length > 80 ? $json.output.summary.slice(0,80) : ($json.output?.summary || '') }}
needs_review  : {{ !['결제','계정','상품','배송','기타'].includes($json.output?.category)
                 || !['긍정','중립','부정'].includes($json.output?.sentiment)
                 || !['상','중','하'].includes($json.output?.urgency)
                 || !$json.output?.summary
                 || $json.output.summary.length > 80
                 || typeof $json.output?.needs_review !== 'boolean'
                 || $json.output?.needs_review === true }}
```

`?.`(optional chaining)로 LLM 응답이 아예 없거나 필드가 누락돼도 에러 없이 기본값으로 대체되고, 허용값을 벗어난 필드가 하나라도 있으면 `needs_review`가 자동으로 `true`가 된다. `urgency`는 자신의 값이 허용값을 벗어난 경우에만 `"중"`으로 대체되며, 검증에 실패해도 워크플로우는 중단되지 않고 해당 건도 예외 없이 시트에 저장된다.

#### Step 6: 결과 저장
`분석결과 저장`(Append Row) 노드가 접수번호(`VOC-yyyyMMdd-HHmmss` 형식), 원본 데이터, LLM 분류 결과, 검증 플래그를 "분석결과" 시트에 한 행으로 추가한다.

#### Step 7: Discord 긴급 알림 (조건부)
`긴급도 분기`(If)가 `urgency == "상"`인 건만 true로 분기하여 `긴급 알림 발송`(Discord, **Webhook URL 방식**)으로 알림을 전송한다. `중`, `하` 건은 알림을 보내지 않는다.

```
🚨 긴급 VOC 접수
```
접수번호 : VOC-20260810-001
분류     : 결제 / 부정
요약     : 결제는 완료됐으나 주문 내역에 없고 고객센터 연결 불가
원문     : (200자까지, 초과 시 말줄임)
접수시각 : 2026-08-10 14:32
```
```

### 3-2. 처리 단계: n8n 워크플로우

| # | 노드명 | 타입 | 기능 | 비고 |
|---|---|---|---|---|

### 3-3. 저장 단계: Google Sheet (분석 결과)

시트 함수 또는 필터 뷰로 다음과 같은 집계가 가능하다.
- `urgency = "상"` 인 행만 필터 → 긴급 건 목록
- `needs_review = TRUE` 인 행만 필터 → 검증 실패/재확인 필요 건
- `category`별 COUNTIF → 문의유형 분포
- `sentiment`별 COUNTIF → 감정 분포

## 부록: 트러블슈팅

**Q. Google Form 응답이 Sheet에 안 나타남**
폼 편집 화면 → 응답 탭 → "Sheets에 연결" 버튼으로 스프레드시트를 연동했는지 확인한다.

**Q. n8n 워크플로우가 자동으로 실행되지 않음**
Google Sheets Trigger가 Manual Trigger가 아닌 Poll 방식 트리거로 설정되어 있는지, 우측 상단이 Published(Active) 상태인지 확인한다.

**Q. 동시에 여러 건을 제출하면 일부가 사라짐**
필터가 걸린 Get Row(s) 노드는 입력 아이템 수만큼 안정적으로 반복 실행되지 않을 수 있다. 필터 없는 전체 조회 + If 조건 내 `.some()` 배열 탐색 방식으로 바꾸면 아이템 수와 무관하게 안전하게 동작한다.

**Q. Discord 알림이 오지 않음**
1. 워크플로우가 Published(Active) 상태인지 확인
2. "분석결과" 시트에 새 행이 생겼는지 확인 — 안 생겼으면 트리거/중복확인 로직 문제
3. 생긴 행의 `urgency`가 "상"인지 확인 — "중"/"하"면 알림 조건 자체가 불성립(정상)
4. Discord 노드의 Connection Type이 Webhook으로, Credential이 올바른 Webhook URL로 연결되어 있는지 확인
5. 같은 물품번호+이메일로 재테스트 중이면 중복 차단으로 조용히 종료된 것일 수 있음

**Q. Gemini 모델 호출이 404로 실패할 때**
Google이 모델을 종료(deprecate)하는 경우가 있다. Gemini API 문서(https://ai.google.dev/gemini-api/docs/deprecations)에서 현재 사용 가능한 최신 모델명을 확인해 Chat Model 노드의 Model 값을 갱신한다.

**Q. LLM이 허용값을 벗어난 값을 반환할 때**
1차로 Structured Output Parser의 JSON 스키마(enum)가 재시도를 유도하고, 2차로 `최종 데이터 정리` 노드의 표현식이 기본값으로 보정하며 `needs_review=true`로 표시되어 시트에는 정상 저장된다.
